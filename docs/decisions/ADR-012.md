# ADR-012: Automatic CORS and Public QR Origin Resolution

## Status
Accepted

## Context
The API is being deployed independently on Vercel and the web application may be deployed as a separate project. Fixed `CORS_ORIGIN` and `QR_CANONICAL_ORIGIN` variables are easy to mismatch across production, preview, and local environments.

## Decision
- Remove `CORS_ORIGIN` and `QR_CANONICAL_ORIGIN` from required runtime configuration.
- For browser CORS, allow originless native/server-to-server requests, same-origin requests, and the API deployment origins supplied through Vercel system variables. Do not reflect arbitrary origins or use wildcard credentialed CORS.
- The browser calls the same-origin Next.js proxy. The proxy strips browser Origin metadata before calling Express and supplies the actual web origin for QR URL generation.
- QR generation prefers that proxy-supplied public origin, then a validated same-origin browser Origin, then Vercel deployment metadata/request host.
- Native callers without web-origin context use the Vercel production domain/request-host fallback. When creating cards from a mobile client, verify that the chosen public web site is available at that fallback domain.

## Consequences
- Operators do not need to maintain `CORS_ORIGIN` or `QR_CANONICAL_ORIGIN`.
- Browser cross-origin direct calls to the API are intentionally not enabled by default; the same-origin proxy is the supported web path.
- The public URL embedded in QR cards follows the web origin when cards are created through the web dashboard or native app after initial setup.
