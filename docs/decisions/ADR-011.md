# ADR-011: MySQL and Prisma ORM

## Status
Accepted; supersedes ADR-003's PostgreSQL provider decision. The existing image-storage decision is implemented with MySQL's LONGBLOB type.

## Context
Connect Me is deploying the API as a Vercel Function and will use a managed MySQL database. Prisma generates database-specific migrations, so PostgreSQL migration SQL cannot be applied to a MySQL database.

## Decision
- Use the Prisma MySQL connector with a fresh MySQL migration baseline.
- Use MySQL 8.4 for local Compose development and a managed MySQL service in hosted environments.
- Keep schema changes managed by Prisma Migrate: generate and review migrations in development, commit migration SQL, and use `prisma migrate deploy` for production.
- Store optional image bytes in the existing separate `submission_images` table; Prisma's MySQL mapping uses `LONGBLOB`.
- Use a new, empty MySQL schema for the new migration history. Moving any existing PostgreSQL data requires a separately planned export/import; the provider switch is not an in-place migration.

## Consequences
- Runtime `DATABASE_URL` must be a MySQL connection URL (`mysql://...`).
- Queries must use Prisma features supported by the MySQL connector. String search uses the database collation instead of PostgreSQL-only `mode: "insensitive"`.
- Production migrations remain explicit deployment steps and do not run on API startup.
